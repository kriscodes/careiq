# ADR-009: Identifier Strategy

**Status:** Accepted

## Context

CareIQ requires a consistent strategy for identifying database records and domain entities.

Identifiers may be referenced across database relationships, backend services, APIs, background jobs, audit records, integrations, and future applications.

CareIQ is designed as a multi-tenant platform that may evolve into multiple applications and services.

The identifier strategy should provide globally unique identifiers while remaining consistent across the CareIQ platform.

CareIQ also integrates with external systems that maintain their own identifiers, including Clerk and future healthcare or practice management systems.

## Decision

CareIQ will use UUIDv7 as the default primary key strategy for CareIQ database tables and domain entities.

UUIDv7 identifiers will be generated by PostgreSQL by default.

Application code should normally create CareIQ records without generating their primary identifiers.

The database will generate the identifier when a record is created.

### Default Identifier Strategy

UUIDv7 will be the default primary key for CareIQ entities, including domain entities that may be referenced by:

- Database relationships.
- APIs.
- Background jobs.
- Audit records.
- Integrations.
- Future applications or services.

Examples include:

- Practices.
- Patients.
- Providers.
- Appointments.
- Tasks.
- Integrations.
- Audit events.

### Identifier Exceptions

UUIDv7 is the default identifier strategy but is not an absolute requirement for every database table.

A natural or composite key may be used when it provides a clearly simpler or more appropriate representation of the record's identity.

Examples may include simple relationship tables or controlled reference data.

Any departure from the default UUIDv7 strategy should be intentional and justified by the domain model or database design.

### API Identifiers

CareIQ primary identifiers may be exposed directly through CareIQ APIs.

The primary database identifier will normally also serve as the CareIQ API identifier.

CareIQ will not introduce separate public identifiers by default.

A separate public identifier may be introduced when a specific architectural, security, interoperability, or product requirement justifies it.

### External Identifiers

Identifiers owned by external systems will remain separate from CareIQ identifiers.

External identifiers must not replace CareIQ's internal primary identifiers.

Examples may include:

- Clerk User IDs.
- Clerk Organization IDs.
- Electronic health record identifiers.
- Practice management system identifiers.
- Other third-party integration identifiers.

External identifiers will be stored as references or mappings to the corresponding CareIQ entities when required.

CareIQ remains responsible for generating and managing its own internal entity identifiers.

## Consequences

CareIQ will have a consistent default identifier strategy across its domain model.

Database-generated identifiers reduce the need for application code, services, or clients to implement and maintain identifier generation logic.

UUIDv7 provides globally unique identifiers that can be safely referenced across APIs, background jobs, integrations, and future distributed services.

Using UUIDv7 identifiers avoids exposing sequential database identifiers through CareIQ APIs.

Using the same identifier internally and through APIs reduces unnecessary identifier mapping and simplifies application development.

The default strategy allows exceptions for tables where a natural or composite key provides a simpler and more appropriate representation of identity.

External system identifiers remain distinct from CareIQ identifiers, reducing coupling between CareIQ's domain model and third-party systems.

The exact PostgreSQL mechanism used to generate UUIDv7 identifiers will be defined during database implementation.
