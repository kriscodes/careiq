# ADR-010: Audit Logging Architecture

**Status:** Accepted

## Context

CareIQ requires a robust audit architecture to provide accountability, traceability, security, and forensic evidence for meaningful actions and data changes.

CareIQ is being designed as a healthcare-focused, multi-tenant platform that may manage sensitive information and integrate with external systems.

The platform must be capable of building a clear and reliable picture of significant activity.

For meaningful operations, CareIQ should be able to determine:

- Who performed an action.
- What action was performed.
- When the action occurred.
- Which Practice or tenant was involved.
- Which entity or data was affected.
- Why the action occurred when that information is available.
- Whether the action was initiated by a user, system, service, background job, administrator, or integration.
- What data actually changed.
- What the previous and resulting values were when appropriate.
- Which request, workflow, or transaction caused related activity.

CareIQ must distinguish between operational logging and auditability.

Application logs answer questions such as:

> What happened to the system?

Audit records answer questions such as:

> Who did what, to which data, when, and from what context?

Application logs alone are insufficient to provide a reliable audit trail.

CareIQ also requires more than a simple record that a database row changed.

The application understands the business meaning and intent behind an operation, while PostgreSQL can independently provide evidence of the actual data mutation.

For example, an application may record:

```text
Action: patient.contact_information_updated

Actor: User
Reason: Patient provided updated contact information
```

While PostgreSQL may independently record:

```text
Operation: UPDATE
Table: patients

Changed:
phone_number
old → new
```

Together, these records provide a stronger and more complete history than either mechanism alone.

CareIQ has also established requirements for tenant isolation, PostgreSQL Row-Level Security, RBAC, and transaction-scoped context in previous architectural decisions.

The audit architecture must work consistently with those decisions.

## Decision

CareIQ will use a hybrid audit architecture.

The architecture will combine:

1. Application-level audit events.
2. Database-level mutation evidence generated by PostgreSQL triggers.

These mechanisms serve different purposes and are not required to duplicate one another exactly.

The application layer records the business intent and context of meaningful actions.

The database layer independently records evidence of actual data mutations.

Related records should be connected using correlation and transaction context when available.

The overall objective is to provide a robust and reconstructable history of meaningful CareIQ activity.

## Audit Architecture

CareIQ will distinguish between four related but separate concerns.

### Application Logs

Application logs support:

- Debugging.
- Monitoring.
- Error investigation.
- Performance analysis.
- Operational troubleshooting.

Application logs are not the authoritative audit system.

They may contain references to requests, correlation identifiers, or audit events but must not replace the Audit domain.

### Application Audit Events

Application audit events capture the business meaning and intent behind significant actions.

They answer questions such as:

- Who initiated the action?
- What business action occurred?
- Which entity was involved?
- Which Practice was involved?
- Why did the action occur when that information is available?
- What was the outcome?
- Which request or workflow initiated the operation?

Examples may include:

```text
patient.created
patient.updated
patient.transferred

appointment.created
appointment.cancelled

practice.member_added
practice.member_removed

role.changed
permission.changed

integration.connected
integration.disconnected
```

The application layer is responsible for understanding and recording the business meaning of these actions.

### Database Mutation Evidence

Database mutation evidence captures what actually changed within PostgreSQL.

It answers questions such as:

- Which table changed?
- Which record changed?
- Which database operation occurred?
- When did the mutation occur?
- What was the previous state when applicable?
- What was the resulting state when applicable?
- Which transaction performed the mutation?
- Which Practice, actor, or correlation context was associated with the transaction when available?

Database mutation evidence provides an independent record of the actual data mutation.

### Customer-Facing Activity History

Customer-facing activity history is a controlled projection of protected audit information.

It exists to provide useful operational visibility to authorized Practice users without exposing the complete forensic audit trail.

Customer-facing activity history is not a separate source of truth or a separate logging system.

It is derived from protected audit information through approved CareIQ backend access paths.

## Dedicated Audit Domain

CareIQ will maintain a dedicated Audit domain within the primary PostgreSQL database.

The Audit domain will use a dedicated PostgreSQL schema:

```text
audit
```

Audit data will remain logically separated from CareIQ application domain data.

The conceptual structure is:

```text
CareIQ PostgreSQL

public
│
├── practices
├── patients
├── providers
├── appointments
├── tasks
└── other application domain tables

audit
│
├── events
├── changes
└── database_records
```

The exact table structure may evolve as the CareIQ domain develops.

## Audit Events

`audit.events` represents meaningful application-level audit events.

Audit events should support information including:

- Audit event identifier.
- Timestamp.
- Practice identifier when applicable.
- Actor type.
- Actor identifier.
- Action.
- Entity type.
- Entity identifier.
- Outcome.
- Reason or business context when available.
- Correlation identifier.
- Relevant metadata.

Actor types must support more than human users.

Examples may include:

```text
user
system
background_job
integration
service
administrator
```

This allows CareIQ to distinguish between actions such as:

```text
User updated patient information.
```

and:

```text
Integration synchronized patient information.
```

or:

```text
Background job performed a scheduled update.
```

## Audit Changes

`audit.changes` represents meaningful changes associated with an application audit event.

Audit changes may include:

- The affected field or attribute.
- Previous value when appropriate.
- New value when appropriate.

Conceptually:

```text
Audit Event:
patient.updated

Changes:

phone_number
old → new

address
old → new
```

Audit changes should support understanding what meaningfully changed without unnecessarily duplicating entire records.

## Database Audit Records

`audit.database_records` represents independent database-level evidence of mutations.

These records will be generated through PostgreSQL triggers for applicable domain tables.

Database audit records may capture:

- Database operation.
- Affected table.
- Entity identifier.
- Practice identifier when applicable.
- Timestamp.
- Previous state or relevant previous values.
- New state or relevant new values.
- Transaction context.
- Actor identifier when available.
- Actor type when available.
- Correlation identifier when available.

Database audit records provide evidence of actual mutations regardless of the business meaning assigned by the application.

## PostgreSQL Audit Triggers

PostgreSQL triggers will be used to generate database-level mutation evidence.

Audit triggers should remain intentionally simple.

Their responsibility is to record facts about database mutations.

Triggers must not become a hidden application business-logic layer.

Audit triggers must not:

- Perform authorization decisions.
- Implement business workflows.
- Make business decisions.
- Send notifications.
- Call external services.
- Trigger unrelated application behavior.
- Replace application-level audit events.

The architectural principle is:

> Triggers record evidence. They do not contain business logic.

The application remains responsible for business behavior.

The database trigger remains responsible for recording the mutation evidence.

## Audit Context

CareIQ should establish relevant audit context within the PostgreSQL transaction when available.

Transaction-scoped context may include:

```text
practice_id
actor_id
actor_type
correlation_id
```

The application may establish this information through transaction-scoped PostgreSQL configuration or another approved transaction-scoped mechanism.

Conceptually:

```text
BEGIN

Establish tenant context
Establish actor context
Establish correlation context

Perform authorized operation

PostgreSQL trigger records mutation evidence

COMMIT
```

The transaction-scoped context must not persist across pooled database connections.

Database audit triggers may read the available transaction context when generating mutation evidence.

This allows database evidence to be connected to the actor and request responsible for the mutation.

## Correlation

CareIQ will support correlation identifiers for meaningful operations when appropriate.

A correlation identifier allows related activity to be connected across multiple layers.

For example:

```text
correlation_id: req_123
```

may connect:

```text
User Action
    │
    ├── Application Audit Event
    │
    ├── Database Mutation
    │
    ├── Background Processing
    │
    ├── Integration Activity
    │
    └── Application Logs
```

This provides a broader picture of an operation rather than isolated records.

Correlation identifiers should support investigation of:

- User actions.
- API requests.
- Background jobs.
- Integration activity.
- Database mutations.
- Related system activity.

## Relationship Between Audit Records

Application audit events and database mutation evidence serve complementary purposes.

They should not be forced into a single record or required to duplicate one another perfectly.

The relationship is conceptually:

```text
Application Intent
        │
        ▼
   audit.events
        │
        ▼
   audit.changes


Actual Database Mutation
        │
        ▼
audit.database_records


        └───────┬───────┘
                │
        Correlation Context
                │
                ▼
      Reconstructable History
```

Application audit events explain what the application intended and why.

Database audit records provide evidence of what PostgreSQL actually mutated.

## Audit Record Immutability

Audit records are append-only and immutable.

Audit records must not be modified or deleted during normal CareIQ application operation.

Normal application database roles must not have permission to:

- Update audit records.
- Delete audit records.

Immutability must be enforced through database permissions and access controls rather than relying solely on developer conventions.

The conceptual access model is:

```text
Audit Writer
    │
    └── INSERT

Authorized Reader
    │
    └── SELECT

Normal Application Role
    │
    ├── UPDATE → Denied
    └── DELETE → Denied
```

Audit records may only be written through explicitly authorized application or database mechanisms.

## Audit Data Retention

CareIQ audit data will have a minimum retention baseline of six years.

Longer retention periods may apply based on:

- Applicable laws or regulations.
- State or jurisdictional requirements.
- Contractual obligations.
- Customer requirements.
- Legal holds.
- Other applicable retention obligations.

The six-year baseline is not intended to override a longer applicable requirement.

Audit records must not be deleted simply because the minimum retention period has elapsed.

If audit records eventually become eligible for disposition, that process must occur through an explicitly authorized retention and disposition process.

The process must account for all applicable requirements and legal holds.

Audit retention and disposition must not be implemented as ordinary application behavior.

CareIQ does not establish automatic deletion of audit records as part of normal application workflows.

Future architectural or compliance decisions may define:

- Archival strategies.
- Legal hold mechanisms.
- Retention classifications.
- Approved disposition processes.
- Long-term storage strategies.

## Sensitive Data Handling

Audit logging must improve accountability without creating unnecessary copies of sensitive information.

Audit records should contain only the information required to establish accountability and explain the relevant action or mutation.

The Audit domain must support selective handling of sensitive values.

Depending on the field and applicable requirements, audit records may:

- Record that a field changed without storing the value.
- Mask values.
- Redact values.
- Store metadata describing the change.
- Store only the portions of a value necessary for accountability.

Conceptually:

```text
Field:
social_security_number

Action:
changed

Old Value:
[REDACTED]

New Value:
[REDACTED]
```

The exact handling of sensitive fields may vary according to the data classification and applicable security, privacy, regulatory, or contractual requirements.

Audit logging must not become an uncontrolled duplicate store of sensitive CareIQ data.

## Customer-Facing Activity History

Practice administrators may access customer-facing activity history for their authorized Practice.

Customer-facing activity history must:

- Be limited to the authorized Practice.
- Respect CareIQ tenant isolation.
- Respect RBAC authorization.
- Be accessed through approved CareIQ backend services.
- Be presented as an appropriate projection of protected audit information.

Client applications must not directly query the `audit` schema.

The conceptual access path is:

```text
Practice Administrator
        │
        ▼
CareIQ API
        │
        ├── Authorization
        ├── Tenant Isolation
        └── Activity Projection
                │
                ▼
             audit.*
```

Customer-facing activity history may provide information such as:

```text
10:42 AM

Maria updated John Smith's contact information.
```

It must not automatically expose:

- Raw database records.
- Internal table implementation details.
- Internal transaction information.
- Internal correlation identifiers.
- Security metadata.
- Trigger-generated forensic details.
- Cross-tenant information.
- Other protected audit information.

Customer-facing activity history is a controlled view of protected audit information.

It is not a separate source of truth.

## Protected Audit Access

Protected audit data contains the detailed information required for security, forensic investigation, platform accountability, and authorized audit review.

Protected audit access is separate from ordinary Practice administration.

A Practice Administrator must not automatically receive unrestricted access to:

```text
audit.events
audit.changes
audit.database_records
```

General platform administration also does not automatically imply unrestricted access to the complete protected audit trail.

Access to protected audit data requires explicit authorization.

## Audit Administrator

CareIQ will support a dedicated platform-level Audit Administrator capability.

An Audit Administrator, or an equivalent explicitly authorized role, may access the complete protected audit trail across CareIQ tenants.

The conceptual permission for this capability is:

```text
audit:platform:read
```

This permission must be granted explicitly.

The Audit Administrator capability is separate from:

- Regular user access.
- Practice Administrator access.
- General platform administration.

This separation follows the principle of least privilege.

A platform administrator may manage platform configuration or customers without automatically receiving unrestricted access to protected forensic audit information.

The conceptual access model is:

```text
Regular User
    │
    └── No direct audit access


Practice Administrator
    │
    └── Customer-facing activity history
        for the authorized Practice


Platform Administrator
    │
    └── Platform administration
        without automatic unrestricted audit access


Audit Administrator
    │
    └── Protected audit access
        across authorized CareIQ tenants
```

Future RBAC decisions may define additional audit permissions, including permissions for:

```text
audit:activity:read
audit:practice:read
audit:platform:read
```

The exact permission model may evolve while preserving the separation between customer-facing activity history and protected forensic audit access.

## Auditing Audit Access

Access to protected audit information is itself a meaningful action and must be audited.

When protected audit records are accessed, CareIQ should record relevant information including:

- Authorized actor.
- Actor type.
- Access time.
- Access context.
- Scope of access when appropriate.
- Correlation identifier when available.

This creates an auditable record of who accessed the audit system itself.

Conceptually:

```text
Audit Administrator
        │
        ▼
Views Protected Audit Data
        │
        ▼
Audit Access Event Created
```

## Cross-Tenant Audit Access

Normal tenant-scoped application access must not provide unrestricted access to audit information belonging to other Practices.

Cross-tenant access to protected audit data requires explicit platform-level authorization.

Actors with `audit:platform:read`, or an equivalent explicitly authorized capability, may access protected audit information across tenants only through controlled and auditable access paths.

Cross-tenant audit access must not bypass CareIQ authorization controls.

## Consequences

CareIQ will maintain a dedicated Audit domain within the primary PostgreSQL database using a separate `audit` schema.

The architecture separates:

- Application logs.
- Application audit events.
- Database mutation evidence.
- Customer-facing activity history.

Application audit events provide business meaning, actor context, intent, reason, and operational context.

PostgreSQL triggers provide independent evidence of actual database mutations.

Simple database triggers avoid creating a hidden business-logic layer inside PostgreSQL.

Transaction-scoped tenant, actor, and correlation context can connect database mutations to the request or workflow that caused them.

Correlation identifiers make it possible to reconstruct a broader picture of meaningful operations across application activity, database mutations, background jobs, integrations, and logs.

Audit records are append-only and immutable during normal CareIQ operation.

Normal application roles cannot update or delete audit records.

CareIQ establishes a minimum six-year baseline for audit retention while allowing longer legal, regulatory, contractual, customer, or legal-hold requirements to take precedence.

Audit data handling minimizes unnecessary duplication of sensitive information and supports masking, redaction, and selective value recording.

Practice administrators can access appropriate customer-facing activity history for their authorized Practice without receiving unrestricted access to protected forensic data.

Protected audit access is explicitly separated from ordinary Practice and general platform administration.

A dedicated Audit Administrator capability can access the complete protected audit trail through explicit authorization such as:

```text
audit:platform:read
```

Access to protected audit information is itself auditable.

The architecture introduces additional complexity in:

- Database triggers.
- Transaction context management.
- Database permissions.
- Audit data storage.
- Retention and archival.
- Sensitive data handling.
- Access control.
- Audit event design.

This complexity is accepted because CareIQ requires a robust and trustworthy foundation for accountability, security, investigation, and future compliance requirements.

All future CareIQ domains and workflows involving meaningful security, administrative, sensitive-data, or domain actions should be designed to integrate with the Audit architecture defined in this decision.
