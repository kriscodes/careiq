# v0.1.0 — Interview baseline

**Date:** 2026-10-03

**Stage:** Initial SDLC baseline; interview demo; synthetic data only

**Tag:** [`v0.1.0`](https://github.com/kriscodes/careiq/tree/v0.1.0)

**Baseline:** [`7a20802`](https://github.com/kriscodes/careiq/commit/7a208022cbc7ba739a94b352f721a9e157aa360f) on `main`, plus the release-documentation commit(s).

## Summary

Version 0.1.0 establishes the current CareIQ interview demo as the starting point for the software development lifecycle. It gives us a named baseline to demonstrate, collect feedback against, and improve in later releases. It includes the existing v0.1 interface and the security hardening merged before this release.

This is an early development release for synthetic demonstrations. The version records what exists; it does not mark the planned readiness workflow or real-patient launch as complete.

## Included

### Interview workflow

- Clerk sign-in, active organization selection, and mapping to an internal practice.
- Create, list and search patients within the selected practice.
- Create and list appointments, navigate days/weeks, and retain records after refresh.
- A light front-desk workspace with centered creation dialogs and practice-scoped selection.
- Optional reviewer notes explaining the architecture. These are static illustrations, not live telemetry.

### API and database foundation

- Express/TypeScript API, Next.js/React web application, and PostgreSQL/Drizzle in a pnpm workspace.
- Server-derived practice context, transaction-scoped tenant context, forced row-level security, and patient/practice relationship constraints.
- Administrator create permissions and member read-only access, enforced by the API and reflected in the web controls.
- Tenant-scoped durable retry protection, metadata-only clinical audit writes, input limits, and bounded list pagination.
- Restricted runtime database grants, database-connectivity health checks, and versioned migrations through `0015` (16 migrations in total).
- Automated CI for migrations and replay, lint, type checks, tests, builds, and production dependency auditing.

### Related marketing code

The repository also contains the CareIQ Labs marketing site, its shared interview-request contract and public intake endpoint. The recorded live marketing deployment follows a separate branch. Intake and indexing remain disabled; this release does not claim successful live intake/retry/deletion acceptance or a marketing redeployment.

## Known limitations and follow-up

- Finish hosted direct-API member write-denial, deliberate cross-practice requests and same-key retry acceptance. Automated coverage and browser demonstrations do not replace these remaining live checks.
- Complete production authentication provider settings and user/practice mappings; the working deployment still uses development authentication.
- Configure independent encrypted backups, scheduling, failure alerts, expiration, recovery-key handling and restoration from that storage.
- Complete customer exports, retention/hold controls and deletion replay after restoration. No clinical purge is enabled.
- Complete marketing intake configuration, review/deletion procedures and live submission/retry/deletion acceptance before enabling intake and indexing.
- Patient editing/deletion and appointment rescheduling/cancellation, availability, conflict prevention and reminders remain outside this slice. Times use the browser's timezone; practice-timezone support remains future work.
- Appointment readiness rules, next-action guidance, EHR/file ingestion, document collection, insurance/referral workflows, staff administration, audit-review UI and automated communication remain future work.
- Real-patient use remains outside this release's approved scope; the remaining hosting, agreement and operating requirements are tracked separately.

## Deployment and recovery

No new migration, credential switch or data conversion is required to record v0.1.0. The tag snapshots the repository; it does not prove that every hosted component runs that exact commit. Use the deployment report for component-specific evidence.

For later deployments, follow the [development/deployment guide](../development.md) and [backup and retention plan](../backup-retention.md). Restore the prior known-good application deployment only when compatible with the current schema. Do not reverse migrations or restore over shared data merely to change an application version.
