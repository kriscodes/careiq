# Owner-controlled security checklist

Prepared during the October 17, 2026 security review of the canonical CareIQ checkout. These steps require your decisions, provider-account authority, spending approval or designation of a trusted administrator. Application code cannot establish these settings on your behalf. An unchecked item is not a claim that a provider is insecure; it means this review has not verified that control in the intended hosted environment.

Keep credentials, recovery codes, customer identifiers and patient records out of this checklist and Notion. Record a redacted result and the location of protected evidence instead.

## Before inviting practices or storing real patient information

| Priority | Action requiring your authority | Completion evidence | Application connection |
| --- | --- | --- | --- |
| P0 | Protect the accounts controlling Clerk, hosting/database, GitHub, DNS, storage, email and your password manager with passkeys or strong MFA. Review existing administrators, active sessions, personal access tokens and recovery routes. Keep recovery material in a separate protected location. | A dated account/access review; a tested recovery procedure; no credentials copied here. | Compromise of these control planes can defeat application isolation. RLS does not constrain the database owner or a privileged infrastructure administrator. |
| P0 | Approve the intended production hosting/storage/provider plans, applicable agreements and responsibility split before PHI use. Confirm who owns access/export, incident response and return/deletion of practice data. | Approved vendor inventory and agreements, scope and environment; practice acceptance. | Earlier project records describe synthetic/demo hosting. This pass does not activate a different plan or authorize real-patient use. HHS explains the applicable cloud-provider/BAA responsibilities and risk analysis in its [cloud guidance](https://www.hhs.gov/hipaa/for-professionals/special-topics/health-information-technology/cloud-computing/index.html). |
| P0 | Deliberately configure the production Clerk instance: sign-in methods, email verification, MFA/session policy, OAuth credentials/domains, redirects and webhook delivery. Approve exact user/organization mappings and staff permissions; never infer membership from an email domain or practice name. | Real owner and staff sign-in/MFA/recovery tests; wrong-account invitation denial; signed webhook/revocation tests. | API and web keys must belong to the same reviewed instance. Key syntax and a successful build cannot prove this. Configure `org:paperwork:manage` only for designated staff with document/configuration access; ordinary administrator status alone must not create that grant. |
| P0 | Approve a private database network and separate runtime, migration/operator and protected audit-reader credentials. Restrict operator access; choose reviewed database TLS and backup settings. | Hosted restricted-role catalog check, network reachability test, operator access record, independently verified restore. | Runtime must be a direct non-owning login without superuser, BYPASSRLS or ownership/privileged-role inheritance. Keep migration and audit-reader credentials separate. Prefer certificate-verified TLS; the documented provider-internal `require` mode is encrypted transport with a different trust boundary. |
| P0 | Approve exact deployed browser/API origins, invitation redirect, proxy ranges and native authorized parties. Remove stale preview/development origins from production configuration. | Allowed-origin success and untrusted-origin denial using the actual deployment; verified proxy topology. | Review `CORS_ORIGINS`, `TRUSTED_PROXY_CIDRS`, `CAREIQ_INVITATION_REDIRECT_URL`, `CLERK_NATIVE_AUTHORIZED_PARTIES` and web API origin. CORS is an additional browser control, not endpoint authorization. Do not add wildcard origins or bypass issuer/origin checks to fix login. |
| P0 | Provision private document storage and its encryption/key policy, access roles, recovery and retention/hold settings. Approve a scanner and isolated rendering/worker environment before enabling those integrations. | Anonymous and cross-practice object access denied; exact-version/hash retrieval; scan/quarantine failure cases; key recovery and restore drill. | Current application authorization and local private-object paths do not configure a cloud bucket, public-access block, KMS, object immutability or independent custody. Keep files outside public/static directories and release only approved versions through authorized access. [OWASP file guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) supports separate protected storage, validation, scanning and object-level authorization. |
| P0 | Authorize and test independent encrypted backups, restore access and alert destinations. Set recovery objectives and approve the applicable retention/hold/export process with practices. | Restore from the independent copy, then replay current deletion/hold instructions before reopening access; documented recovery time/data loss. | Provider-native backups and a local migration replay are useful evidence but do not establish independent recovery, protection against operator compromise or complete record lifecycle enforcement. |
| P0 | Select the email provider and approve sending domain, DNS authentication, allowed sender, verified patient destinations, preferences and generic secure-link content. Approve the corresponding agreements where applicable. | Provider acceptance/webhook/retry/bounce tests, no-PHI content review and proof that revoked access cannot be restored by an old email. | The current completion notification records intent/follow-up and reports an unavailable delivery provider. Real sending, durable workers and reconciliation remain implementation/activation work; credentials alone will not complete them. |

The API is a trusted boundary: it verifies identity and supplies transaction-local actor/practice/location context to the database. Practices never receive database credentials. RLS tests protect against incorrect or missing scope in that model; they do not prove safety after compromise of the API process, its context-setting runtime credential or a privileged operator account. Protecting and rotating those credentials and limiting their network reach are part of the owner-controlled controls above.

## Release and daily operation

- [ ] Require the repository verification job in branch protection, restrict who can merge/deploy and gate hosting deployment on successful checks. Review CI secret access and short-lived deployment identities. A workflow file alone does not configure the required check or hosting gate.
- [ ] Approve the hosted release, maintenance window, recoverable backup and rollback plan. Apply only the complete reviewed migration history through a separate operator identity; run restricted-runtime verification afterward. Local code changes do not update the hosted application automatically.
- [ ] Adopt least-privilege staff onboarding/offboarding and explicit clinical location assignments. Test a second practice and an unassigned/revoked user in the intended environment. Approve who may verify patient self-account access, review demographic candidates and view audit evidence.
- [ ] Approve the signing/consent, language, representative/minor and sensitive-record policies for each supported practice workflow. The implemented single adult-self flow and its age rule are a technical eligibility boundary, not a universal determination of legal signing authority. Unsupported roles must stay blocked until their workflow is implemented and accepted.
- [ ] Choose an actual operating load target: practices, staff active at once, visits/day, patients retained, documents/day and document size. Set an API/DB connection budget across every replica/worker, storage budget and alert thresholds. Repeat the synthetic benchmark on the intended hosting tier with real network/provider latency before capacity acceptance.
The current per-process default is 10 clinical connections and 40 queued checkouts, with a 10-second checkout deadline, 30-second statement deadline, 5-second lock deadline and 30-second idle transaction deadline. Include the separate audit-reader pool (up to 2 connections), each API replica and all workers in the fleet budget. The [100-practice benchmark](../verification/security-load-2026-10-17/database-performance.md) records the measured load and its limits; practice count alone is not a capacity target.

- [ ] Set alerts for authentication failures, authorization denials, unusual document access/export volume, database/pool saturation, slow requests, disk/storage growth, unavailable workers/scanners and backup failures. Choose who receives them and test the alert route. Keep patient payloads, tokens, cookies and raw request bodies out of diagnostics.
- [ ] Keep a separately protected incident runbook: emergency access review, token/credential rotation, patient-link revocation, service containment, evidence preservation, restoration and applicable notification responsibility. Rehearse it with the people who hold the necessary accounts.
- [ ] Protect the development computer: full-disk encryption, screen lock, software updates, restricted local accounts and encrypted/reviewed device backups. Do not use synced project/chat folders as a secret vault or patient-document store. Local `.env` files now have owner-only filesystem permissions; `.local-review` is private and ignored. Development web/API defaults bind to loopback. An explicit API `HOST` is an owner opt-in; do not publish a development instance or proxy it to the internet.
- [ ] Review dependency advisories and approve the release disposition. The current raw production audit still flags two high advisories, `node-forge` and `braces`; their reviewed backport tests pass, but the independent audit remains non-green. The reported upstream fixed versions were unavailable in the registry during this review. See [patch provenance](../../patches/README.md). Do not silence the audit or invent an upgrade version to obtain a green result.

## Evidence to keep for each hosted acceptance

Record the environment and reviewed release identifier, actor role and practice/location scope, action/result, time and protected evidence location. For denied tests, retain status codes and non-sensitive identifiers sufficient to correlate the protected audit. Do not save bearer tokens, sign-in tickets, passwords, cookies, patient names or document bodies in screenshots, CI artifacts or this repo.

At minimum, demonstrate owner/staff login and recovery; no repeated button/loading oscillation; a valid clinical save/reload; explicit allowed and denied document access; restricted one-request access; authenticated library access and revocation; cross-practice/cross-location denial; same-key retries; publication/freeze/signing authority; backup restoration; and a realistic sustained-load run. Separate synthetic component tests, actual isolated database tests and real hosted/provider evidence in the record.

[PostgreSQL's RLS documentation](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) describes owner/BYPASSRLS boundaries. [OWASP's multitenant guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html) recommends server-verified tenant context, transaction-scoped state, object authorization and pooled-connection isolation checks. The concrete CareIQ guards and release procedure are documented in the [API release guide](../api-production-release.md), [Forms Studio implementation](../forms-studio-implementation.md) and [verification index](../verification.md).
